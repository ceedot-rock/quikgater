# Quikgater

Pay-per-fact web fetch for AI agents. Implementation of `fetchgate_v2_1_FINAL.md` (x402 Primitive Spec v2.1, still under its original filename — the spec doc wasn't renamed, only the product/repo), which is the source of truth for architecture/pricing/policy decisions - this README only tracks build status.

**Renamed from Fetchgate to Quikgater, 2026-07-24** — "Fetchgate" collided with an existing company (fetchgate.com, a Webflow file-gating product). GitHub repo, Cloudflare Worker, Queue, R2 bucket, and Fly.io app were all renamed/recreated; old resources were deleted. See the bottom of this file for the verification log from that migration.

## Layout

- `worker/` — `quikgater-worker`, the Cloudflare Worker edge layer (blocklist, robots.txt, rate limit, eventually the x402/cache/queue gate).
- `browser-worker/` — `quikgater-browser-worker`, the Fly.io render service (Layers 2-3: rented render failover, hard fallback).

**Payment gate (not one of the spec's numbered steps, but now built):** `worker/src/payment.ts`, wired into `index.ts` ahead of the Step 1 blocklist check, matching spec §3's architecture diagram order. x402 protocol, scheme `exact`, network `base-sepolia` (testnet — see "Going to mainnet" below), verified live against the real `x402.org/facilitator` (schema pulled directly from `github.com/coinbase/x402/specs`, not from memory). Do not reuse `/home/cee/projects/x402-client` — that's an unrelated Solana payer client, and Quikgater is the payment *verifier*, not a payer.

**Payment-verify rate limit:** `checkPaymentVerifyRateLimit` in `worker/src/ratelimit.ts`, 300 req/min per requester, checked immediately before the facilitator `/verify` call (not after — the point is to bound that outbound network call itself, not just the HTTP response). Deliberately keyed on requester only, not requester+domain like the Step 1 domain limiter — otherwise rotating target domains would dodge it entirely while still hammering the facilitator. 300 (not something tighter) because every request needs its own verification with no session caching, so a legitimate client near the domain limiter's 100/min ceiling - or spread across a few domains - needs real headroom above 100.

**Layer 1 (not one of the 6 numbered steps, but now built):** `worker/src/layer1.ts` - a cheap, direct in-Worker `fetch()` of the target URL (no JS execution, no headless browser), tried before falling back to the paid Layer 2 render pipeline. Rejects and falls through to Layer 2 when the response isn't HTML/text, the extracted text is too short (a JS-shell SPA with nothing server-rendered), or the page looks like an active bot challenge (Turnstile, "just a moment...", etc.) - all covered in `worker/test/layer1.test.ts`. A real title comes from the page's own `<title>` tag, which is actually better metadata than Layer 2 has (`browser-worker` still has no title extraction - see below).

Deliberately attempted only *after* payment is verified and Step 1 has passed, not as a pre-payment price probe - see the comment at the top of `layer1.ts`. That means it doesn't (yet) pass a cheaper price through to the client: the $0.08 miss price is quoted and signed before Layer 1 ever runs, and EIP-3009 can't reduce a signed amount after the fact, so a request Layer 1 successfully serves still settles at the full miss price. What it *does* do: skip the real per-call cost of Browserbase/Steel/Firecrawl whenever a page doesn't need a real headless render, and respond synchronously (200) instead of via the async queue (202 + poll). Passing the savings through to the client would need either a pre-payment probe (which would let an unauthenticated request make Quikgater fetch an arbitrary third-party page for free) or Rail B deposit credits (debit the real cost after settling) - neither exists yet.

**Queue caveat, updated:** the spec reserves the queue for requests that miss Layer 0 (cache) *and* fail Layer 1. Both now exist, so a request only reaches the async queue (Layer 2/3) if a cache lookup, then a real Layer 1 fetch attempt, both come up empty - matching the spec's real layered design, not the "everything goes straight to the queue" state from before Layer 1 existed.

**Cache caveats, stated plainly:**
- **TTL classification is a URL-shape heuristic**, not real content classification (`classifyTtl` in `cache.ts`) - it has no signal from the page itself. Matches the spec's own "start with static map" framing; needs real hit-rate data to tune, not more guessing.
- **No ETag/If-None-Match revalidation.** The spec calls for revalidating on TTL expiry rather than a hard cache-miss; that needs the render pipeline to accept and return conditional-request headers, which `browser-worker`'s `/render` doesn't support (Step 6 gap, not this layer's).
- **R2 bodies can outlive their KV pointer.** KV's own TTL expiry is what makes an entry invisible to `getCached`, but the R2 object isn't cleaned up when that happens - an orphan, not a bug, until something sweeps it (R2 lifecycle rule, or a job keyed off KV expiry events).
- **No title extraction.** `browser-worker` doesn't parse HTML into a real title (Step 6 gap) - `deriveTitle()` falls back to the first Markdown heading, then the URL itself.

**Settlement is now wired and live** (see "Live" below for the real on-chain proof). Two real architectural constraints shaped the design, worth understanding before touching this code:

- **EIP-3009 signs an exact amount - there's no "charge less/more after the fact."** The client's signature is cryptographically bound to a specific `value`; you cannot settle a different amount than what was signed without a fresh signature. This means the price **must** be quoted correctly *before* the client signs, not decided afterward.
- **Cache lookup moved to before the payment gate** (`index.ts`) specifically so the quoted price is correct: cache hit → `$0.0002`, miss → `$0.08`. It's a read-only lookup, so there's no leak in checking it pre-payment - nothing is served until after payment clears.
- **Miss price is still $0.08, not the spec's $0.002 "standard fetch" rate** - even with Layer 1 built (see above), because the price is quoted and signed *before* Layer 1 ever runs, so it has to cover the worst case (a full Layer 2 render, real cost $0.01-0.05). Pricing every miss at $0.002 up front would mean losing money on every request that turns out to need a real render - the same margin bug caught and fixed earlier for Step 5's cost table, now correctly reflected in what's actually charged.
- **Cache hits settle synchronously; misses settle only if the render succeeds - never on total failure.** For a hit, the outcome is already known, so it settles right in `index.ts`. For a miss, settlement is deferred into the queue consumer (`queue.ts`), which only calls `settlePayment` after a provider actually delivers content. If every provider and hard-fallback fail, `settlePayment` is never called at all - the client's signed authorization simply expires unused. That's the only clean way to do "don't charge for nothing" under EIP-3009's exact-amount model; there's no partial-settle or refund primitive to lean on instead.
- **`maxTimeoutSeconds` raised from 60 to 180** to give the deferred-miss path enough runway - queue processing has taken 30s+ under a cold Fly machine in this repo's own testing, and the client's authorization must still be valid when `/settle` finally gets called.
- **Settlement failure despite a successful render is a real edge case, not swallowed.** If `/settle` fails after content was already rendered (expired authorization, facilitator error), the content is still returned - it was already produced, withholding it doesn't get anyone paid - but the job status carries `settled: false` and `settlementError` so the gap is visible, not hidden.

**Rail B: deposit credits (spec §5, core scope now built, 2026-07-24).** `worker/src/credits.ts` (account/balance ledger, KV-backed) + `worker/src/stripe.ts` (real Stripe Checkout integration). An account is just an API key -> balance mapping, no signup flow. Routes:
- `POST /v1/credits/checkout` `{ amountUsd: 5|20|100, apiKey?: string }` - starts a real Stripe Checkout Session for a deposit; mints a new `qg_...` API key (zero balance) if none is provided, so a brand-new user has a key before they've paid anything.
- `POST /v1/stripe/webhook` - real Stripe webhook receiver for `checkout.session.completed`, registered against this Worker's live URL on the account's Stripe dashboard (`we_1TwrE4K8JsmXFzvIYmIxrZru`). Verifies the real HMAC-SHA256 signature (`stripe.ts`, Web Crypto, 5-minute replay tolerance) before crediting anything - unauthenticated requests can't mint credits.
- `GET /v1/credits/balance` (`Authorization: Bearer qg_...`) - checks current balance.
- Any `?url=` fetch request with `Authorization: Bearer qg_...` is billed via credits instead of x402 - the header is checked before X-PAYMENT, so it takes priority if both are somehow present.

**The actual point of Rail B, not just an alternate payment method:** a credits debit has no EIP-3009-style exact-signature constraint - it's just an internal KV write, decided *after* the real outcome is known. That's what finally makes real outcome-based tiered pricing possible (`payment.ts`'s `priceAtomicForTier`, used by `queue.ts`'s `settleBilling`): a Bearer-billed request Layer 1 ends up serving is charged the real $0.002 "standard fetch" rate, not Rail A's pre-quoted $0.08 worst case. A total render failure is even charged the spec's $0.0001 fee ("to cover queue + logs and prevent abuse") - something Rail A structurally can't do, since there's no way to charge a different amount than what was pre-signed. The only pre-check on the credits side is a worst-case balance gate (`balanceAtomic >= MISS_PRICE_ATOMIC`) before any work happens, mirroring why Rail A pre-quotes worst-case too - proving ability-to-pay before doing anything, just via a balance check instead of a signature.

**Credentials note:** `STRIPE_SECRET_KEY` is a real **live-mode** restricted key (`rk_live_...`) on a Stripe account shared with other unrelated projects (wsoap, agentrider, agentmagnet each have their own separate webhook endpoints on the same account - only Quikgater's own endpoint was touched). Set as a real Worker secret via `wrangler secret put`, never in `wrangler.toml`. Local `npm test`/`wrangler dev` use fake values from `worker/.dev.vars` (gitignored) instead.

**Explicitly deferred (not core scope for this pass):**
- **Auto-topup at <$1** (spec §5) - the deposit/checkout/webhook/debit mechanics above are what it would build on top of, but the "automatically charge a saved payment method" part isn't built.
- **Quikgater Pro, $29/mo** (2x rate limit, 7-day cache TTL, email support, `ignore_robots` option) - a separate subscription product, not started.
- **Free tier.** Spec's "100 free cache hits/day/IP" needs an account/IP-quota system that doesn't exist - a cache hit is cheap to serve (no queue, no Fly.io call) but still requires payment via one of the two rails, same as a miss.

**Step 6 caveats, stated plainly:**
- **No `costActual` from any provider, confirmed on real calls, not just from reading docs.** The live test below returned `"costActual":null` from a real successful Browserbase call - checked each provider's response schema beforehand (Browserbase Fetch, Steel `/v1/scrape`, Firecrawl `/v2/scrape`) and none report a per-call dollar cost in the body, and the real response confirmed it. Spec §6's `cost_actual_usd` will stay `null` for L2 until/unless a provider exposes this (or costs get estimated from published pricing instead of measured per-call).
- **No title extraction.** None of the three providers return a distinct page title separate from the markdown body in the shapes used here - `deriveTitle()` (Step 5, `cache.ts`) still falls back to the first Markdown heading, then the URL.
- **API keys are real Fly secrets, not in `fly.toml`.** Set via `fly secrets set`; one (`FIRECRAWL_API_KEY`) came from a "session-specific auth" block in a pasted CLI onboarding document rather than a dashboard-generated key, and may be short-lived/scoped to that session - worth regenerating from the Firecrawl dashboard if it stops working later.

2. **Real webhook signature verification against the live signing secret.** Since actually completing a Checkout Session wasn't going to happen (see above), crediting was proven by constructing a `checkout.session.completed` payload and signing it with the real `STRIPE_WEBHOOK_SECRET` (HMAC-SHA256 per Stripe's documented scheme) exactly the way Stripe itself would, then POSTing it to the live `/v1/stripe/webhook`. `200 {"success":true}` - the endpoint's real signature verification accepted a correctly-signed request. `GET /v1/credits/balance` afterward showed exactly `$5.00` (500 cents × 10,000 = 5,000,000 atomic units) - the crediting math is correct against a real response shape, not just a unit-test fixture. (First attempt at this returned an unrelated `403` from Cloudflare's own edge - Python's default `urllib` User-Agent, not our webhook logic; curl with the identical signed payload got a clean `200`.)
3. **Real tiered pricing, proven with a request about Stripe itself.** Used the now-funded key to fetch `en.wikipedia.org/wiki/Stripe_(company)` via `Authorization: Bearer qg_...`. Result: `tierUsed: "L1"`, `payment: {"method":"credits","debitedAtomic":2000,"newBalanceAtomic":4998000}` - debited exactly **$0.002**, the real Layer 1 "standard fetch" rate, not Rail A's pre-quoted $0.08 worst case. This is the actual thing Rail B exists to prove: a credits debit reflects the real outcome, not a worst-case signature.

Not fired live (deliberately, per the "core scope" decision): the total-failure $0.0001 charge and the render-tier $0.08 credits debit, both already covered by real (unmocked, real-KV) tests in `queue.test.ts` - firing those live would mean actually exhausting a render attempt for no additional proof beyond what Rail A's Layer 2 live test already established.
